# ТСД — точечные исправления и передача на контролируемое боевое тестирование

## Область изменений

Применить `tsd_staging_safety.patch` к актуальному коммиту `e067c0b07f376921770d528cafd6a3c965f0271a`. Патч ужесточает проверки в `portal/tsd-guard/lib/TsdDocumentEngine.php`:

- Только подтверждённый исходный статус `N` допускает изменение приходного документа; `Y` возвращает ранее проведённый результат, `C` отклоняется, прочие значения блокируются.
- Отсутствие `docType=A` отклоняет проведение.
- Пустой достоверный список складов означает отсутствие допустимых складов.
- Неполный ответ `catalog.document.element.list` блокирует добавление строк и требует сверки.

**Важно:** патч не применён к GitHub: у подключённого приложения права только на чтение (GitHub API 403 при создании ветки). Патч составлен по исходным строкам из GitHub; перед применением нужно проверить его в репозитории и тестах.

7. Сохранить SHA сборки, подпись APK, `versionCode`, `versionName`, результат тестов, список проверенных файлов и APK SHA-256 в релизном отчёте.

## Передача для тестирования на боевом ТСД

Использовать **контролируемый пилот**, а не произвольные тесты с реальными остатками. До запуска:

- Сначала подтвердить работоспособность серверного модуля на staging или эквивалентной тестовой базе Битрикс, включая наличие CRest, права, MySQL locks и повторный запрос при тайм-ауте.
- На боевом ТСД проверить установку, вход, экран сканирования, 50–100 сканирований, выход/повторный запуск, перезагрузку, офлайн/онлайн, восстановление списка **без проведения документа**.
- Для теста проведения выделить отдельный разрешённый склад/номенклатуру/тестовый документ, согласовать ответственное лицо и способ сверки/отката. Зафиксировать остатки до и после каждого теста.
- Не проводить конкурентные эксперименты с двумя ТСД на реальных документах, пока серверные endpoint не установлены и не проверены.
- При 409, `RECONCILIATION_REQUIRED`, изменении остатков сверх ожидаемого или потере сканирований остановить тесты и сохранить логи.
